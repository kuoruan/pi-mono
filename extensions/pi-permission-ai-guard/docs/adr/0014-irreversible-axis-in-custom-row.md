# 0014 — the irreversible axis belongs to the custom row

- Status: accepted.
- Context: ADR 0013 raised a reviewer allow that meets proven-irreversible facts to an ask in every mode, on both emission paths, and the release never ran the mode mapping for it. That left `customMode` with a third axis it could not name: the two cut lines measure reviewer doubt, the failure lane measures reviewer absence, and neither can express "the operator accepts this class of irreversible effect". An operator who wanted a custom row to pass such an allow had only the policy gate's per-command allow rules — named commands, not a class decision — while a custom row that wanted to forbid the class outright had no expression at all.
- Decision: `customMode` gains `onIrreversibleEffect` (`allow` | `defer` | `deny`), defaulting to `defer`, read only when `mode` is `custom` like the rest of the block. Every built-in rung rules `defer`, so the shipped ladder keeps the invariant the live round established and only a written custom row can choose otherwise. The ruling is its own axis rather than a rung on the suspicion line: doubt and proven irreversibility are different questions, and forcing the choice onto the cut lines would either reopen the silent pass under `auto` (if placed low) or turn a built-in ask into a deny (if placed high). The redundancy check compares the whole row including the ruling, so a custom row that redraws a built-in rung but rules the floor differently is not reported as that rung. The release applies the ruling before the mapping: `allow` lets the ordinary allow path run with the record annotated (`floorFacts` plus `floorRuling`), `defer` asks with the floor's own reason, `deny` blocks with the floor's own reason plus the agent instruction. The screen's hard deny and the upstream policy decision stay outside this axis — covering those would change hard-deny authority itself, which is a separate decision with its own threat model.
- Consequences: an existing `customMode` block without the new key parses to `defer` and behaves exactly as before, so no migration. A custom `allow` reopens, per class, the three silent-pass shapes the anchored round caught — the operator's explicit, recorded choice rather than a reviewer's silent one, and the record says whose choice it was. A custom `deny` refuses an authorized irreversible action outright, stricter than any built-in rung. The cache keeps storing the reviewer's verdict, so a replay rules the same way as the fresh pass under the same custom row.
- Alternatives considered: letting the two cut lines govern the floor (rejected: the axis has no order to cut, and either placement breaks a built-in behaviour — `auto` would allow or deny where it now asks); a boolean "floor off" flag (rejected: it expresses only the waiving direction and leaves the forbidding direction without a voice, while a three-outcome knob matches the `onReviewFailure` precedent); folding screen hard-deny into the same knob (rejected: that changes hard-deny authority, which ADR 0006 reserves to the deterministic screen in every mode, and it deserves its own risk review rather than riding along); leaving the operator to per-command policy allow rules only (rejected: those name commands, and the request was class-level control of the mode's own row).
